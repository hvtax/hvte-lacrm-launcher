# Irene's routine release runbook

Use this when the owner asks to add/remove an action or change a label/URL. One-time owner setup in RELEASE.md must already be complete. Routine work uses your connected GitHub access and the owner's repository Actions secrets; **you never receive, view, or handle AMO credentials**.

## Limits

Never change the add-on ID, update_url, permissions, host, release tooling, or update mechanism as part of a routine actions request. Never put client information in source or reports. Stop and ask the owner if signing fails or a requested action needs a new permission. If an ambiguous request lacks a target URL or label, ask for that information rather than inventing it. The repository must remain public `hvtax/hvte-lacrm-launcher`.

## Exact sequence

1. Open the correct repository and its default branch. Check no release workflow is in progress. In a local checkout, run `git pull --ff-only` and `git fetch --tags origin`; start with a clean working tree. Via the GitHub API, read the latest default-branch commit and files first and use that head as the parent of your change.
2. Read src/actions.js and manifest.json. Apply the owner's requested action change **only in src/actions.js**. Preserve list order unless asked to reorder. Use `type: "action"`, a unique label, an HTTPS `url`, and optionally `openIn: "newTab"` or `"sameTab"`. The exact `<CONTACTID>` token means the current contact is required; omit it for a plain launcher. Preserve Cognito prefill fragments unless explicitly asked to change them. Do not paste a live client's URL.
3. Increment PATCH in manifest.json (for example 1.0.1 → 1.0.2). It must exceed all release tags and any version the owner says AMO has already signed. Add one short newest-first CHANGELOG.md entry for this version. For a routine request these are the **only three files** to edit. Do not edit package.json or updates.json.
4. Review the diff and exact URLs. If you have a local checkout with Node 22+ and npm, run `npm ci`, `npm test`, and `npm run lint`. All must pass. If operating solely through GitHub APIs, review syntax carefully; the release workflow runs the same mandatory checks before signing. No local signing is required.
5. Commit and push the three files to the default branch with exactly this message format: `release: v<version> - <one-line summary>`. For example: `release: v1.0.2 - Add office help action`. Do not create a tag or release. GitHub API users should create one commit containing all three files, with the reviewed branch head as parent; refuse a stale-head overwrite.
6. Dispatch `.github/workflows/release.yml` **manually on the default branch**. In the GitHub UI: Actions → Release Firefox add-on → Run workflow → default branch → Run workflow. With GitHub CLI: `gh workflow run release.yml --repo hvtax/hvte-lacrm-launcher --ref <default-branch>`. API equivalent: `POST /repos/hvtax/hvte-lacrm-launcher/actions/workflows/release.yml/dispatches` with JSON `{"ref":"<default-branch>"}`. Substitute the actual default branch from repository metadata.
7. Identify the newly dispatched run by branch/source commit and timestamp. Watch it to completion in Actions, or list runs with `gh run list --workflow release.yml --repo hvtax/hvte-lacrm-launcher`, then `gh run watch <run-id> --repo hvtax/hvte-lacrm-launcher --exit-status`. If it fails, capture the failing step name and its error **verbatim** for the owner (redact any unexpectedly exposed sensitive data). Do not blindly rerun: AMO may already have consumed that version. Stop and ask the owner on a signing failure. See RELEASE.md for owner-led partial-release recovery.
8. Wait for the automatically triggered **Publish update feed** (`pages.yml`) run to succeed. Do not assume the first workflow's success means the public feed is current. If Pages fails, report its failing step verbatim; do not declare the release complete.
9. Verify **anonymously, with no GitHub login or Authorization header**, that `https://hvtax.github.io/hvte-lacrm-launcher/updates.json` returns the new version under `hvte-lacrm-launcher@hvtaxexperts.com`. Follow that entry's update_link and download `hvte-lacrm-launcher-<version>.xpi`. Confirm the SHA-256 matches update_hash. You can use a private browser window or anonymous `curl -fL`; authenticated GitHub API access alone is not a valid check. Allow Pages deployment/cache propagation and retry before reporting a stale feed as a failure.
10. Pull the workflow's updates.json commit into your checkout before the next task. Report: **version**, **what changed**, **release URL** (`https://github.com/hvtax/hvte-lacrm-launcher/releases/tag/v<version>`), verification result, and the sentence **“staff copies update themselves within about a day”**. Never include client IDs or credential values.

## Rollback

Firefox does not downgrade through updates.json. To undo an actions change, restore the previous action list in src/actions.js, use a **new higher** manifest version, add a CHANGELOG entry explaining the rollback, and follow the same sequence. Never repoint the feed to an older version, delete a release tag to reuse a version, or overwrite a signed asset. A signing failure, consumed version, or new-permission request goes to the owner.
